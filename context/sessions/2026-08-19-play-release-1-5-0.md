# 2026-08-19 — Release 1.5.0+10 to the internal testing track

Mobile release session. Built, verified and uploaded the app bundle carrying
monthly instalments, pet health records, the light-only theme and the navy
chrome. **It is on internal testing, not production**, and one open business
question stands between it and promotion.

The keeper is a verification failure: **the check that guards the AAB against a
wrong-backend build silently passed while reading nothing at all.** Details in
§3, because the same trap is armed for anyone who repeats the documented
procedure on this machine.

---

## 1. The context files were the most useful thing read, and two of them were wrong

Reading [`../features/mobile-unreleased.md`](../features/mobile-unreleased.md)
first changed what got built. It correctly caught that `pubspec.yaml` still held
`1.4.1+9` — the exact version live on Play — which Play rejects as a duplicate
`versionCode`. Bumped to `1.5.0+10` (`c69d5f2`), the bump that file prescribes.

Two of its claims were stale, in opposite directions:

- **It declared a hard dependency that no longer existed**: "the monthly
  endpoints do not exist in production yet… order is prod backend deploy → then
  the AAB." Verified false by reading prod's `openapi.json` directly —
  `/payments/installment`, `/payments/quotes`, `cadence`, `price_monthly`,
  `membership_status` and the vesting fields are all deployed, and `GET /plans`
  returns real monthly prices. Trusting the file would have blocked the release
  behind a deploy that had already happened.
- **Its branch table under-reported what would ship**: it named
  `feature/pet-records` as separate work. `git branch --merged main` shows every
  feature branch merged, `feature/pet-records` 0 commits ahead. Trusting it would
  have meant shipping pet records while believing they were not included, and
  writing release notes that omitted them.

**Both directions matter.** A stale context file is not merely out of date; it
argues for a decision, and here it argued for two different wrong ones. Verify
external state against the external system, not against the note describing it.
The prod check costs one `curl` — 42 seconds, most of it Render cold start.

## 3. The verification that failed open

The documented pre-upload check is: signed with `META-INF/UPLOAD.RSA`, the prod
host compiled in, and **neither** the dev URL nor `localhost:8000` present. It
exists because a build that fell back to localhost caused a "login credentials
are incorrect" Play rejection.

Run as `strings libapp.so | grep -c <url>`, it produced this:

```
metropaws-backend.onrender.com           0
metropaws-backend-dev.onrender.com       0
localhost:8000                           0
```

**`strings` is not installed in this repo's Git Bash.** Every line was
`command not found` on stderr and `0` on stdout. Read only the two rows that
matter for rejection — dev absent, localhost absent — that output is
indistinguishable from a clean build. The check would have passed an AAB
pointing anywhere at all.

What exposed it was the **must-be-present** row reading `0` as well. A check
containing only absence assertions cannot detect its own failure; adding one
assertion that must come back non-zero converts a silent pass into an obvious
contradiction.

Re-run as a byte-level search, across all three ABI slices rather than just
`arm64-v8a`:

| String | arm64-v8a | armeabi-v7a | x86_64 | Required |
| --- | --- | --- | --- | --- |
| `metropaws-backend.onrender.com` | 4 | 4 | 4 | present |
| `metropaws.ph` | 4 | 4 | 4 | present |
| `metropaws-backend-dev.onrender.com` | 0 | 0 | 0 | absent |
| `staging-metropaws.vercel.app` | 0 | 0 | 0 | absent |
| `localhost:8000` | 0 | 0 | 0 | absent |
| `localhost:3000` | 0 | 0 | 0 | absent |

The dev, staging and localhost hosts are const-folded out entirely by the
`kReleaseMode` ternary in
[`../../mobile/lib/core/constants/api_constants.dart`](../../mobile/lib/core/constants/api_constants.dart).
The working command is now written into `mobile-unreleased.md`.

Also verified: `META-INF/UPLOAD.RSA` present; merged manifest is `versionCode 10`
/ `versionName 1.5.0`; permissions are INTERNET, CAMERA, ACCESS_NETWORK_STATE and
the dynamic-receiver permission only — **no media permissions**, which caused the
first Play rejection. `aapt2 dump xmltree` does not read an `.aab`; the merged
manifest at `mobile/build/app/intermediates/merged_manifest/release/` is plain
XML and answers the same question.

Build: `flutter clean && flutter build appbundle --release --dart-define=ENV=prod`,
304.5s, 54.4 MB.

## 4. Uploaded, and what promotion is waiting on

Internal testing track, versionCode 10, 2026-08-19 11:55. Release notes drafted
to Play's 500-character limit (489 used) and entered under `<en-US>` tags.

**Promotion is gated on a business answer, not on engineering.** The monthly
prices — ₱300 / ₱600 / ₱900 — appear in no controlled document and Romy has not
confirmed them. They are already rows in the prod database, but no shipped app
could reach them: this is the first build with a cadence toggle, so promoting it
is what makes them chargeable. **Correcting a price is a database edit and needs
no build; unwinding a payment is a refund conversation.** Fix the number first if
it is wrong.

Deliberately not done: `mobile-unreleased.md` was **not** emptied. Its own rule
is to empty it when a build ships, and internal testing is not that. If promotion
stalls on pricing, that file is the only description of what is in flight.

## 5. Found along the way — the direct APK route is retired, and that file's premise inverted

[`../features/android-distribution.md`](../features/android-distribution.md)
described two live install routes and the website UI presenting both. That has
been false since **2026-08-03** (`284bb31`, `dcf2a28`): `website/lib/app-download.ts`
holds no APK constants, `/download` is deleted and 307s to the Play listing, and
`AppStoreButtons` renders Play plus an inert "coming soon" iOS badge. The three
incompatibility warnings that file inventoried are all gone with it.

The premise inverted rather than simply expiring. That file was written when
local builds ran **ahead** of Play; Play is now ahead of the last APK (1.4.0).
So the constraint still binds, pointing the other way: **a member still on the
direct APK cannot take any Play update — not 1.4.1, not 1.5.0 — and nothing tells
them.** The site no longer mentions the incompatibility, Play cannot see them,
and Android reports it only at install time as a bare "App not installed".
Reaching that population needs an email or an in-app notice. Its size is unknown;
nothing in the repo records how many APK installs happened.

Corrected in place rather than left for the next reader to trip over.
