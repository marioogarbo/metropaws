## Architecture at a Glance

```
Widget (UI) → BLoC (event) → ApiService (HTTP) → FastAPI Backend
                    ↓
             BLoC (state) → Widget rebuilds
                    ↓
          AuthStorage (secure token read/write)
```

**One BLoC per feature.** No cross-feature BLoC dependencies. Shared state (auth token, current user role) lives in `AuthStorage` and is read directly by `ApiService`.

## Key Business Logic

- **Pet as Hero:** Member UI MUST center the pet (name, photo, breed, sessions). Owner info is secondary.
- **QR ID:** Members display their `qr_token` as a QR code using `qr_flutter`. The token is fetched from the backend — NEVER generated client-side.
- **Service Sessions:** `remaining_sessions` comes from the backend. The mobile app reads and displays it only — NEVER mutates it directly. Only the Admin "Deploy Service" flow triggers a backend decrement.
- **Plan payments (PayMongo) — money path, treat as critical:** A plan is granted server-side via FOUR independent paths, all in `backend/app/routers/payments.py`: (1) webhook — **dead on the dev/staging env** (PayMongo delivers to one URL); (2) client poll `GET /payments/{id}` — reconciles with PayMongo server-side on every call; (3) the browser return page `/payments/return/success?payment_id=…` — reconciles + deep-links `metropaws://payment/...` back to the app; (4) profile-load safety net — `GET /members/me` reconciles the member's recent (≤7 days, ≤5) pending payments, so simply reopening the dashboard self-heals a paid-but-stuck plan (added 2026-07-07 after an Add-a-Pet checkout was PAID on PayMongo but sat `pending`). On mobile, BOTH checkout flows MUST keep the `paymentId` from `createCheckout` and poll: `PlanSelectionScreen` polls via `MemberBloc` (`PaymentStatusPolled`); `AddPetScreen` polls directly via `ApiService.getPayment` (3s timer started when "Complete Payment" is tapped, plus an `AppLinks` listener for the return deep-link; timer + subscription cancelled in dispose). NEVER discard the payment id after `createCheckout` — that regression is exactly what stranded a paid member. Both flows also gate payment behind `AgreementCheckbox`.
- **Pack Discount (2026-07-27):** 15% off the 2nd/3rd pet's plan when it's strictly cheaper than the member's best active plan — computed SERVER-SIDE only (`backend/app/domain/pricing_utils.py`). The app NEVER derives a price: plan screens display quotes from `GET /payments/quotes` (`PlanQuote` model, `ApiService.fetchPlanQuotes({petId})`; `petId` = pet being (re)activated so it's excluded from the anchor set, null in Add-a-Pet). `PlansLoadRequested(petId:)` → `PlansLoaded.quotes` (Map by planId) feeds `plan_selection_screen.dart`; `add_pet_screen.dart` fetches quotes directly alongside its plans. Quote fetch failure MUST degrade to full-price display (never block the screen) — the backend still applies the discount at checkout, so the charge is never wrong. Both `_PlanCard`s + the confirm sheet show strikethrough full price / final price / save badge; badge text uses gold (dark mode) vs goldDark (light) for contrast.
- **Plan upgrade/renewal (2026-07-28):** Rules live SERVER-SIDE in `backend/app/domain/plan_term_utils.py` — mid-term only a strictly higher plan while benefits are untouched; same/lower plans wait for the renewal window (last 30d) or expiry; every grant REPLACES benefits and restarts the 365-day year. The app only displays state: `PlanQuote` now carries `eligible`/`eligibility` (`new|upgrade|renewal|current_plan|lower_plan|benefits_used`)/`isCurrent` (tolerant defaults for old backends), and `plan_selection_screen.dart` renders a current-plan header ("active until" = `planActivatedAt + 365d`, display-only), a "Current plan" badge (outranks "Popular"), state-aware CTAs (Upgrade/Renew/Switch), and a pre-payment "benefits will be replaced" note on the confirm sheet. **Ineligible plans are HIDDEN, not shown disabled** (client decision 2026-07-29): `_PlansBody._visiblePlans` keeps only `eligible || isCurrent` cards (a null quote — fetch failure — fails open), so same/lower plans and usage-blocked upgrades disappear; when anything was hidden because benefits were already used, one explanatory line renders above the list instead. `_PlanCard` therefore never sees `lower_plan`/`benefits_used`. Entry point for pets WITH plans: `_PlanActionLink` on the Home pet card (under the QR CTA) — "Upgrade plan" / "Renew now" (last 30d) / "Plan expired — Renew", all via the same `_openPlanSelection`. Expired plans: `WalletPet.planStatus`/`planExpiresAt` (from `/members/me/wallet`) gate the Reimbursements Submit tab (inline banner + disabled button — the server 400s anyway) and tag the Benefits hub `WalletPetCard` ("Expired — renew"). Ineligible purchases attempted anyway (stale/old app) get a 409 whose `detail` surfaces verbatim via the existing CheckoutFailed snackbar.
- **Monthly memberships (2026-08-17, backend live on dev):** A plan can be paid **annually or in monthly instalments** (Agreement Rev. 5A §5.2–§5.10). Backend design is in `context/features/monthly-subscriptions.md` — read it before touching this. Mobile side: `PlanSelectionScreen` shows a `_CadenceToggle` (annual/monthly) **only when a visible plan has `Plan.priceMonthly`**; the choice is screen-level presentation state (`_cadence`, like `_selectedPlan`) and rides to the server as `CheckoutRequested(cadence:)` → `ApiService.createCheckout(..., cadence:)`. **The Pack Discount is annual-only** — it is 15% off a YEAR, so every discount affordance (strike-through, badge, savings line) is suppressed when monthly, on both the card and the confirm sheet. The sheet must always quote the figure the server is about to charge; do not let it fall back to the annual quote. **A monthly member is not immediately covered** — the first instalment buys app access only, and benefits vest after N consecutive payments (6/8/10 planned, 3/3/4 emergency, per plan). Say that before payment, not after. Continuing payments go through `InstallmentRequested(petId)` → `ApiService.payInstallment` → `POST /payments/installment`, which **reuses the existing Checkout* states** so the launch-and-poll handling is unchanged — never discard the returned `paymentId` (same money-path rule as `createCheckout`). `WalletPet` carries `membershipStatus` / `membershipStatusLabel` (§5.7 — render the server's label verbatim, never hardcode the wording) plus `subscriptionNextDueOn` / `subscriptionPaymentsMade`; `isMonthly` keys off the payment count because the wallet only lists pets that already hold a plan. **Nothing bills automatically** — there is no scheduler behind the API and no saved card while QR Ph is the only live method, so the member paying from the app is the mechanism, not a fallback.
- **Pet health records (2026-08-17):** `HEALTH RECORDS` on `pet_profile_screen.dart` holds the **vaccination card** and **care notes**. Both are member-editable; **no admin or clinic upload path exists**, by decision (Mario, 2026-08-17: "only user can upload this for now") — so never write copy telling a member to ask their clinic or support to do it. That exact string was the bug: the empty state said "Contact your clinic to upload your vaccination record" while clinics have no upload capability and the member had no route at all, because `_VaxSection` was a `StatelessWidget` that only ever *viewed*. It is now stateful and mirrors `_PhotoCompletionSection` deliberately — same re-entrancy guard, same `ApiService.maxUploadBytes` check, same `picked.name` extension trick (never `.path`, which is a blob URL on web), same `onPetUpdated` hand-back. Reuse that pattern for any third upload rather than inventing a variant. `ApiService.uploadVaxCard` now returns the refreshed `Pet` — it returned `void` for months, which is precisely why it sat with zero callers: a caller had nothing to hand back, so the screen could never show what it had just uploaded. The existing-card tile carries a quiet **Replace card** action, because a card goes stale at the next round of shots and without it the member hits the same dead end one upload later. **Care notes moved out of `PET DETAILS`** into this section: they are health information, they were hidden entirely when empty (so nothing revealed the field existed), and editing routes to the existing `PetFormScreen` rather than adding a second editor for one field. Images only, matching registration — the backend also accepts PDF, but two pickers for one task is worse than the missing format. **The larger gap is unchanged:** Manual §5 promises a vaccination *record* (vaccine name, date given, next due, history, reminders) and the model still holds a single `vax_card_url` image — that needs a `PetRecord` table, see `context/features/document-system-alignment.md` item 7.

## BLoC Conventions

- Events MUST be past-tense actions: `LoginSubmitted`, `PetLoaded`, `ServiceDeployed`
- States MUST be descriptive: `AuthInitial`, `AuthLoading`, `AuthSuccess`, `AuthFailure`
- Each BLoC file MUST export only its own events and states — no cross-feature BLoC dependencies
- MUST use `BlocProvider` at the route level, not the widget tree root (unless state is shared across routes)
- MUST use `BlocBuilder` for rebuilds, `BlocListener` for side effects (navigation, snackbars)

---

## API Conventions

- MUST route all API calls through `core/services/api_service.dart` — NEVER call `http` directly from a BLoC or widget
- `ApiService` injects the Bearer token automatically from `AuthStorage` — NEVER attach tokens manually
- MUST parse the `detail` field from FastAPI error responses and surface it via `AuthFailure(message)` or equivalent failure state
- Base URL MUST be configured in `core/constants/api_constants.dart` only — change it there and nowhere else

- **LIGHT MODE ONLY (client decision, 2026-08-17).** `main.dart` pins `themeMode: ThemeMode.light` regardless of the device setting or any saved preference, and the Appearance picker is gone from the Account tab. Do NOT design or test dark variants for new work, and do NOT reinstate the picker without asking. `buildDarkTheme()` and `ThemeCubit` remain wired but unreached — dark mode is finished work that may return, and deleting it would mean rebuilding every dark-surface decision. Restoring is two edits: return `themeMode` to the `MaterialApp` and put the picker back. Existing `brightness == Brightness.dark` branches in widgets are harmless dead paths; leave them.
- **The app chrome is NAVY; the content field is cream (2026-08-17).** `appBarTheme` is navy app-wide, the Home tab opens with a navy header block (greeting + name + Founding badge + PawPoints, rounded foot at 28), and `_MpNavBar`'s capsule is navy. That trio is the 30% band of a 60/30/10 split — before it, navy appeared once on the Home screen and gold was doing navy's structural work (~10 gold marks on one screen). Six screens were ALREADY overriding the app bar to navy by hand (notifications, paw_points, reimbursement, payout_details, pet_profile, deploy_service); the theme now matches what the app was already doing, and those local overrides are harmless duplicates.
  - **`gold` on `navy` is 2.9:1 — it fails even the 3:1 UI floor.** Gold reads on the near-black tier cards (`0xFF111219`), NOT on navy. On any navy surface use `AppColors.white` for emphasis, `AppColors.onNavyMuted` (4.6:1) for muted labels, and a SOLID gold fill with `AppColors.text` on top (6.1:1) when something must be gold. This is why the active nav tab is white, not gold, and why the raised Claim circle wears a cream ring (7.4:1) rather than a bar-colored one — the ring, not the gold, delineates the control.
  - **`gold` on WHITE is 2.7:1.** Small gold text on the light Standard card must be `AppColors.goldDark`. `_DigitalIdCard` derives `cardAccent` per surface and passes it to `_WalletSummaryRow` / `_FileClaimLink`; `wallet_category_card.dart` already did this.

Pinning it breaks those. AppBar-less screens keep whatever the last screen set: the auth screens open on a full-bleed photo (light icons are right), and `payment_result_screen` carries an explicit `AnnotatedRegion` because its top is cream.

Progress-bar fills, section eyebrows, pagination dots, and the greeting paw are ink/navy — they were spending the accent on structure.
